Overview

이 프로젝트는 Minecraft류 세계를 위한 Diffusion·Mixture-of-Experts·Vision-Language 에이전트를 내세웠지만, 실제로는 환경이 랜덤 픽셀을 돌려주고 모든 행동을 무시하던 저장소에서 출발했다. 이를 테스트된 세 갈래 파이프라인으로 만들었다. 기호 기반 테크 트리 위의 DEPS 방식 LLM 플래너, PyTorch로 Crafter 픽셀을 학습하는 MoE·Diffusion 정책, 10억 스텝 레퍼런스 런을 재현하기 위한 순수 JAX Craftax 학습기다.

최종 주장은 의도적으로 좁게 잡았다. 4코어 CPU에서 각 파이프라인이 실제로 학습하고, 결정론적으로 동작하며, 중단 후에도 비트 단위로 똑같이 이어서 학습한다. 레퍼런스의 학습 종료 수치를 맞추는 일은 GPU 실행이 필요하며, 이 구성은 그 실행을 명령어 한 줄로 줄여 둔다.

진단, 환경, 에이전트, 학습 인프라, 자동 테스트 58개, 그리고 이 페이지까지 한 저장소 안에서 처음부터 끝까지 구현했다.

Key Results

Environment

기호 기반 테크 트리 세계

측정 결과

랜덤 픽셀 환경을 도구·작업대·화로·연료 규칙이 실제로 적용되는 Gymnasium 테크 트리로 교체했다. 기본 태스크 성공이 0/6에서 6/6이 되었고(나무 반블록 3스텝, 다이아몬드 34스텝), 행동 30%가 무작위로 실패해도 재계획으로 6/6을 유지했다.

세계가 행동에 반응하기 전까지는 에이전트를 평가할 수 없다. 어떤 실험이든 첫 테스트는 "스크립트 정책으로 풀 수 있는가"여야 한다.

Training method

Diffusion 모방학습

측정 결과

Key Features

1. 테크 트리 환경과 DEPS 루프

플래너가 계획을 세우면 파서가 이를 하위 목표(Mine cobblestone x6)로 바꾸고, 셀렉터가 다음 목표를 고르고, 컨트롤러가 행동한다. 실패가 반복되거나 한 목표에 너무 오래 머물면 인벤토리와 오류 메시지를 담아 재계획한다. 모든 규칙을 하나의 순수 함수에 두어 환경, 컨트롤러의 선행 조건 탐색, 규칙 기반 플래너가 같은 규칙을 공유한다.

diffu_moe_vlm/core.py
def apply_action(inventory, verb, item):
    if obtain_method(item) != verb:
        return dict(inventory), False, f"cannot {verb} {item}"
    tools, consumed = action_requirements(verb, item)
    missing = {req: amount - inventory.get(req, 0)
               for req, amount in {**tools, **consumed}.items()
               if inventory.get(req, 0) < amount}
    if missing:
        desc = ", ".join(f"{n} {k}" for k, n in missing.items())
        return dict(inventory), False, f"cannot {verb} {item}: missing {desc}"
    new_inv = dict(inventory)
    for req, amount in consumed.items():
        new_inv[req] -= amount          # 도구는 필요하지만 소모되지 않음
    new_inv[item] = new_inv.get(item, 0) + output_quantity(verb, item)
    return new_inv, True, ""

2. Mixture-of-Experts 몸통

노이즈를 더한 top-k 게이트가 각 관측 임베딩을 MLP 전문가 4개 중 2개로 보낸다. Switch Transformer 방식의 균형 손실(완전 균형이면 1, 한 전문가로 몰리면 E)이 전문가가 고르게 쓰이도록 하고, 층별 전문가 사용률을 학습 중에 기록한다. model.trunk=mlp로 일반(dense) 몸통과 비교할 수 있다.

diffu_moe_vlm/nn/moe.py
probs = logits.softmax(dim=-1)                          # (B, E)
top_vals, top_idx = probs.topk(self.top_k, dim=-1)       # (B, k)
weights = top_vals / top_vals.sum(dim=-1, keepdim=True)
expert_out = torch.stack([e(x) for e in self.experts], dim=1)
chosen = expert_out.gather(1, top_idx.unsqueeze(-1).expand(-1, -1, x.shape[-1]))
y = (weights.unsqueeze(-1) * chosen).sum(dim=1)

load = F.one_hot(top_idx[:, 0], self.num_experts).float().mean(0)
aux_loss = self.num_experts * (load * probs.mean(0)).sum()

3. 행동 묶음 위의 Diffusion 정책

8스텝 행동 묶음을 [-1, 1]로 스케일한 원-핫 (H × A) 텐서로 표현한다. FiLM으로 조건을 받는 디노이저가 노이즈 섞인 묶음, Diffusion 단계, 이미지 임베딩으로부터 깨끗한 묶음을 예측한다. 실행할 때는 간격을 둔 DDIM 10단계로 묶음을 샘플링하고, 앞의 4개 행동만 실행한 뒤 다시 샘플링한다.

diffu_moe_vlm/nn/diffusion.py
x0 = self.encode_actions(actions)                     # one-hot * 2 - 1
t = torch.randint(0, self.num_diffusion_steps, (x0.shape[0],))
noise = torch.randn_like(x0)
ab = self.alphas_bar[t].view(-1, 1, 1)
x_t = ab.sqrt() * x0 + (1 - ab).sqrt() * noise
pred = self.denoiser(x_t, t.float(), self.encoder(obs))
return F.mse_loss(pred, x0 if self.prediction_type == "sample" else noise)

4. JAX Craftax 학습기

환경 스텝, GAE, PPO 업데이트를 하나의 jit 안에서 jax.lax.scan으로 돌린다. 끝난 환경은 매번 월드를 새로 만들지 않고, 소수의 새 월드 풀에서 하나를 받아 간다. 학습은 체크포인트 단위의 청크로 나아가며 파라미터, 옵티마이저, 환경 상태, 난수 상태를 모두 저장하므로, 다시 실행하면 멈춘 지점에서 정확히 이어진다.

Problem Solving

Problem 1: 절대 성공할 수 없는 에이전트

증상

모든 벤치마크 태스크가 999스텝에서 success: false로 끝났고, 전체 벤치마크는 첫 태스크 뒤에 멈췄다.

원인

환경이 np.random.randint 픽셀을 돌려주고 행동 처리 함수가 pass여서 인벤토리가 변하지 않았다. 여기에 폴백 플래너가 자기 프롬프트 템플릿 안의 wooden_slab에 매칭되어 모든 태스크에 나무 반블록 계획을 내놓았고, 계획 텍스트를 리터럴 백슬래시 n으로 나눴으며, 로거가 존재하지 않는 속성을 호출했다.

목표

학습을 붙이기 전에 성공이 가능하고 측정 가능한 세계를 만든다.

해결
  • 도구와 재료 규칙이 적용되는 Gymnasium API 기반 기호 테크 트리 환경.
  • 수량을 고려한 규칙 기반 플래너, 이벤트 기반 하위 목표 완료, 인벤토리와 오류 정보를 담은 재계획.
  • 설정 키, 파싱, 로깅, 데이터 로딩 수정과 패키지 구조·테스트 정비.
결과

기본 태스크 0/6 → 6/6, 행동 30% 무작위 실패에서도 6/6, 플래너 경로 단위 테스트 34개.

Problem 2: 관측을 무시한 Diffusion 정책

증상

학습 손실은 내려갔지만, 서로 다른 행동 묶음이 나와야 하는 어두운 이미지와 밝은 이미지에서 거의 같은 묶음이 샘플링됐다.

원인

노이즈 예측(epsilon) 방식에서는 높은 노이즈 구간의 손실이 깨끗한 원-핫 묶음을 복원하는지에 거의 의존하지 않는다. 그래서 결과를 좌우하는 샘플링 초반 단계가 조건을 거의 반영하지 못했다.

목표

전체 DDPM과 간격을 둔 DDIM 샘플링 모두에서 관측에 따라 달라지는 행동 묶음.

해결

깨끗한 샘플(x0)을 직접 예측하고, 샘플링 때 노이즈를 그로부터 계산한다. 노이즈 예측 방식은 옵션으로 남겼다.

결과

조건 테스트에서 400스텝 학습 후 40/40 정확히 일치(100스텝부터 정답). Crafter Diffusion 모방학습 점수 3.56(PPO 교사 4.63).

Problem 3: 레퍼런스 그래프에 한참 못 미치는 결과

증상

Crafter PPO 런은 EAT_PLANT 0%에 철 도구도 없었는데, 레퍼런스 그래프에는 철 칼과 다이아몬드까지 나왔다.

원인

레퍼런스는 Craftax-Symbolic(기호 관측, 업적 약 65개)을 GPU에서 초당 5만~9.5만 스텝으로 10억 스텝 학습한 런이고, 그래프 x축은 PPO 업데이트 횟수다(10억 ÷ (1024 × 64) ≈ 15,258). 로컬 런은 Crafter 픽셀 10만 스텝으로, 환경도 다르고 데이터는 1만 분의 1이었다.

목표

레퍼런스 설정을 그대로 실행하고 그 결과와 대조할 수 있는 파이프라인.

해결

기본 설정의 순수 JAX PPO·PPO-RNN Craftax 학습기와, 그래프에서 읽은 학습 종료 범위 70개를 담은 레퍼런스 파일 및 compare_craftax_run.py.

결과

CPU에서 초기 학습 순서가 레퍼런스와 일치한다(기본 업적이 먼저 포화되고 나무·돌 도구가 뒤따름). 10억 스텝 비교는 GPU 명령 한 줄만 남았다.

Problem 4: 학습 도중 죽는 런

증상

100업데이트짜리 CPU 런이 세션 시간 제한으로 약 32번째 업데이트에서 중단됐다. 레퍼런스 런도 10개 중 8개가 failed 상태로 끝났다.

원인

학습 전체가 하나의 jit scan으로 돌아가서 끝날 때까지 아무 상태도 저장되지 않았다.

목표

중단된 런을 이어서 학습해도 중단 없이 끝낸 런과 결과가 정확히 같아야 한다.

해결

학습을 N업데이트 단위의 jit 청크로 나누고 청크마다 전체 상태를 저장한다. 같은 명령을 다시 실행하면 그 상태에서 이어진다. 시간 제한이 있는 작업은 max_updates_per_run으로 의도적으로 멈춘다.

결과

한 번에 끝낸 런과 5업데이트마다 프로세스를 바꿔 이어 붙인 런 사이에 기록된 값 390개 중 차이 0개. 단위 테스트로 파라미터가 비트 단위로 같은지도 확인한다.

Problem 5: 태스크를 압도한 호기심 보상

증상

레퍼런스 ICM 런에서 내적 보상은 스텝당 약 7.5까지 오르는데 외적 보상은 0 근처에 머물렀고, PLACE_TABLE마저 0%로 떨어졌다.

원인

스케일을 조정하지 않은 forward 모델 오차를 희소한 태스크 보상에 그대로 더해서, 에이전트가 새로움만 최적화했다.

목표

평균 기여도가 고정되어 있고 태스크 보상에 비해 작은 탐색 보너스.

해결

보너스를 이동평균으로 나눠 평균을 1로 맞추고 0.01을 곱한다. 처음에는 표준편차로 나눴지만, 제곱 오차는 대부분 평균 성분이라 평균이 약 12로 남았다.

결과

정규화된 보너스는 스텝당 평균 0.01, 일반적인 에피소드 기준 약 5로, 수렴 시 20을 넘는 태스크 리턴보다 충분히 작다.

Miscellaneous Trials & Errors

1. 호기심 보상을 표준편차로 정규화한 시도

첫 ICM 수정은 보너스를 이동 표준편차로 나눴다. 그래도 보너스가 스텝당 평균 약 12였다. 제곱 예측 오차는 분산이 아니라 대부분 평균 성분이기 때문이다. 이동평균으로 나누자 스케일이 맞았다.

2. CPU 과다 할당

Crafter PPO 학습 옆에서 테스트를 돌리자 학습 속도가 초당 약 80스텝에서 15스텝으로 떨어졌다. 환경 프로세스 8개와 PyTorch 스레드 풀 2개가 코어 4개를 두고 경쟁했다. 이제 torch_threads 옵션으로 환경 워커 몫의 코어를 남긴다.

3. 레퍼런스 그래프 읽기

처음에는 W&B의 "Step" 축을 환경 스텝으로 읽었다. 실제로는 PPO 업데이트 횟수였고, 15k 업데이트를 10억 스텝에 맞춰 보면서 레퍼런스 런의 배치 크기를 알아냈다.
