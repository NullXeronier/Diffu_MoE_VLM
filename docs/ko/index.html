오픈월드 크래프팅 게임을 위한 계획·학습 에이전트. 장난감 세계 위의 LLM 플래너에서 시작해 JAX로 재현 가능한 Craftax 학습까지.

코드 재현성 보고서 연구 노트

Overview

출발점은 Minecraft류 세계용 Diffusion·Mixture-of-Experts·Vision-Language 에이전트라고 소개된 저장소였다. 막상 열어 보니 환경은 랜덤 픽셀만 돌려주고 행동은 전부 무시했다. 이 저장소를 테스트가 붙은 파이프라인 세 개로 다시 세웠다. 기호 테크 트리에서 계획하는 Describe, Explain, Plan and Select 방식 LLM 플래너, Crafter 픽셀로 학습하는 PyTorch MoE·Diffusion 정책, 10억 스텝 레퍼런스 런을 재현하려고 만든 순수 JAX Craftax 학습기다.

여기서 주장하는 것은 많지 않다. 4코어 CPU에서 세 파이프라인 모두 실제로 학습하고, 같은 시드면 같은 결과가 나오며, 중간에 끊겨도 비트 단위로 똑같이 이어진다. 레퍼런스의 최종 수치까지 맞추려면 GPU로 돌려야 하는데, 그 실행은 명령어 한 줄이면 된다.

문제 진단부터 환경, 에이전트, 학습 인프라, 자동 테스트 68개, 이 페이지까지 모두 한 저장소에서 직접 만들었다.

Key Results

Environment

기호 기반 테크 트리 세계

측정 결과

랜덤 픽셀 환경을 걷어내고 도구·작업대·화로·연료 규칙이 실제로 돌아가는 Gymnasium 테크 트리를 넣었다. 기본 태스크 성공이 0/6에서 6/6으로 올랐고(나무 반블록 3스텝, 다이아몬드 34스텝), 행동 30%를 일부러 실패시켜도 재계획으로 6/6을 지켰다.

배운 점

세계가 행동에 반응하지 않으면 에이전트를 평가할 방법이 없다. 그래서 어떤 실험이든 "스크립트 정책으로 풀리는가"부터 확인한다.

Planning

수량을 고려한 Describe, Explain, Plan and Select 루프

측정 결과

단계를 빠뜨린 계획을 주면, 컨트롤러가 고른 하위 목표만 실행할 때는 재계획 한도 5회를 다 쓰고 실패한다. 컨트롤러가 선행 재료까지 알아서 모으게 하면 같은 계획이 성공한다. 이 차이로 계획 품질과 제어 품질을 따로 잴 수 있다.

Algorithm

Crafter 픽셀 위의 MoE PPO

측정 결과

Training method

Diffusion 모방학습

측정 결과

PPO demonstration으로 학습한 Diffusion 정책은 점수 3.56, 리턴 3.55를 냈다(teacher는 3.60). clean sample을 직접 예측하게 바꾼 뒤로는 조건 테스트에서 action chunk가 40/40 모두 맞았다.

Diffusion 손실이 낮아도 조건을 안 볼 수 있다. 목표가 원-핫이면 노이즈 예측(epsilon) 방식은 노이즈가 큰 구간에서 clean sample을 거의 붙잡지 못한다.

Infrastructure

Key Features

1. 테크 트리 환경과 Describe, Explain, Plan and Select 루프

플래너가 계획을 세우면 파서가 하위 목표(Mine cobblestone x6)로 쪼개고, 셀렉터가 다음 목표를 고르면 컨트롤러가 움직인다. 실패가 거듭되거나 한 목표에 너무 오래 붙잡혀 있으면 인벤토리와 오류 메시지를 넣어 다시 계획한다. 규칙은 순수 함수 하나에 모아 두었다. 환경도, 컨트롤러의 선행 조건 탐색도, 규칙 기반 플래너도 이 함수 하나를 본다.

diffu_moe_vlm/core.py
def apply_action(inventory, verb, item):
    if obtain_method(item) != verb:
        return dict(inventory), False, f"cannot {verb} {item}"
    tools, consumed = action_requirements(verb, item)
    missing = {req: amount - inventory.get(req, 0)
               for req, amount in {**tools, **consumed}.items()
               if inventory.get(req, 0) < amount}
    if missing:
        desc = ", ".join(f"{n} {k}" for k, n in missing.items())
        return dict(inventory), False, f"cannot {verb} {item}: missing {desc}"
    new_inv = dict(inventory)
    for req, amount in consumed.items():
        new_inv[req] -= amount          # 도구는 필요하지만 소모되지 않음
    new_inv[item] = new_inv.get(item, 0) + output_quantity(verb, item)
    return new_inv, True, ""

2. Mixture-of-Experts trunk

노이즈를 섞은 top-k 게이트가 관측 임베딩마다 MLP expert 4개 중 2개를 고른다. Switch Transformer식 load-balancing loss(완전히 고르면 1, 한 expert에 몰리면 E)로 expert가 골고루 쓰이게 하고, 층마다 expert 사용률을 학습하면서 남긴다. model.trunk=mlp로 바꾸면 일반(dense) trunk와 비교할 수 있다.

diffu_moe_vlm/nn/moe.py
probs = logits.softmax(dim=-1)                          # (B, E)
top_vals, top_idx = probs.topk(self.top_k, dim=-1)       # (B, k)
weights = top_vals / top_vals.sum(dim=-1, keepdim=True)
expert_out = torch.stack([e(x) for e in self.experts], dim=1)
chosen = expert_out.gather(1, top_idx.unsqueeze(-1).expand(-1, -1, x.shape[-1]))
y = (weights.unsqueeze(-1) * chosen).sum(dim=1)

load = F.one_hot(top_idx[:, 0], self.num_experts).float().mean(0)
aux_loss = self.num_experts * (load * probs.mean(0)).sum()

3. action chunk 위의 Diffusion 정책

8스텝 action chunk는 [-1, 1]로 스케일한 원-핫 (H × A) 텐서다. 디노이저는 FiLM으로 조건을 받아, 노이즈 섞인 chunk와 Diffusion 단계, 이미지 임베딩을 보고 clean chunk를 맞힌다. 실행할 때는 DDIM 10단계로 chunk를 뽑고, 앞의 4개 행동만 쓴 다음 다시 뽑는다.

diffu_moe_vlm/nn/diffusion.py
x0 = self.encode_actions(actions)                     # one-hot * 2 - 1
t = torch.randint(0, self.num_diffusion_steps, (x0.shape[0],))
noise = torch.randn_like(x0)
ab = self.alphas_bar[t].view(-1, 1, 1)
x_t = ab.sqrt() * x0 + (1 - ab).sqrt() * noise
pred = self.denoiser(x_t, t.float(), self.encoder(obs))
return F.mse_loss(pred, x0 if self.prediction_type == "sample" else noise)

4. JAX Craftax 학습기

환경 스텝, GAE, PPO 업데이트를 jit 하나 안에서 jax.lax.scan으로 돌린다. 에피소드가 끝난 환경은 월드를 새로 만들지 않고, 미리 만들어 둔 몇 개 중 하나를 받아 간다. 학습은 체크포인트 간격만큼 끊어서 진행하고, 끊을 때마다 파라미터·옵티마이저·환경 상태·난수 상태를 전부 저장한다. 그래서 다시 실행하면 멈춘 자리에서 그대로 이어진다.

obs_re, state_re = jax.vmap(self._env.reset_env, in_axes=(0, None))(

rank = jnp.cumsum(done) - 1                                  # 끝난 환경마다 서로 다른 월드

state = jax.tree.map(select, state_re, state_st)

    num = min(chunk, stop_at - next_update)
    runner, _ = jax.block_until_ready(train.run_updates(runner, next_update, num))

Problem Solving

Problem 1: 절대 성공할 수 없는 에이전트

증상

벤치마크 태스크가 전부 999스텝에서 success: false로 끝났고, 벤치마크 전체는 첫 태스크를 넘기지 못하고 멈췄다.

원인

환경은 np.random.randint 픽셀을 돌려줬고 행동 처리 함수는 pass뿐이라 인벤토리가 그대로였다. 게다가 폴백 플래너는 자기 프롬프트 템플릿 안의 wooden_slab을 매칭해서 어떤 태스크든 나무 반블록 계획을 냈다. 계획 텍스트는 리터럴 백슬래시 n으로 잘랐고, 로거는 없는 속성을 불렀다.

목표

학습을 붙이기 전에, 성공할 수 있고 성공을 잴 수 있는 세계부터 만든다.

해결
  • 도구·재료 규칙이 들어간 기호 테크 트리 환경(Gymnasium API).
  • 수량을 따지는 규칙 기반 플래너, 아이템을 얻는 순간 끝나는 하위 목표, 인벤토리와 오류를 넣은 재계획.
  • 설정 키·파싱·로깅·데이터 로딩 버그 수정, 패키지 구조와 테스트 정리.
결과

기본 태스크 0/6 → 6/6. 행동 30%를 무작위로 실패시켜도 6/6. 플래너 경로 단위 테스트 34개.

Problem 2: 관측을 무시한 Diffusion 정책

증상

학습 손실은 내려갔다. 그런데 어두운 이미지와 밝은 이미지에서 서로 다른 action chunk가 나와야 하는데도 거의 같은 chunk가 나왔다.

원인

노이즈 예측(epsilon) 방식에서는 노이즈가 큰 구간의 손실이 clean one-hot chunk를 되살렸는지와 거의 상관이 없다. 그래서 결과를 사실상 정하는 샘플링 초반 단계가 조건을 거의 보지 않았다.

목표

전체 DDPM으로 뽑든 DDIM으로 건너뛰며 뽑든, 관측이 바뀌면 action chunk도 바뀌어야 한다.

해결

clean sample(x0)을 바로 예측하고, 샘플링할 때 노이즈는 거기서 거꾸로 계산한다. 노이즈 예측 방식은 옵션으로 남겨 두었다.

결과

조건 테스트에서 400스텝 학습 뒤 40/40 일치(100스텝째부터 정답). Crafter Diffusion 모방학습 점수 3.56(PPO teacher 4.63).

Problem 3: 레퍼런스 그래프에 한참 못 미치는 결과

증상

로컬 Crafter PPO 런은 EAT_PLANT가 0%였고 철 도구는 하나도 없었다. 레퍼런스 그래프에는 철 칼과 다이아몬드까지 있었다.

원인

레퍼런스는 Craftax-Symbolic(기호 관측, 업적 약 65개)을 GPU에서 초당 5만~9.5만 스텝으로 10억 스텝 학습한 런이었다. 그래프 x축도 PPO 업데이트 횟수였다(10억 ÷ (1024 × 64) ≈ 15,258). 로컬 런은 Crafter 픽셀 10만 스텝이었으니 환경부터 달랐고 데이터는 1만 분의 1이었다.

목표

레퍼런스 설정을 그대로 돌리고 결과를 레퍼런스와 맞대어 볼 수 있어야 한다.

해결

기본 설정으로 도는 순수 JAX PPO·PPO-RNN Craftax 학습기를 만들었다. 그래프에서 읽어 낸 학습 종료 범위 70개는 레퍼런스 파일에 담고, compare_craftax_run.py로 비교한다.

결과

CPU에서 본 초기 학습 순서가 레퍼런스와 같다(기본 업적이 먼저 차고 나무·돌 도구가 뒤를 잇는다). 10억 스텝 비교는 GPU에서 명령 한 줄만 돌리면 된다.

Problem 4: 학습 도중 죽는 런

증상

100업데이트짜리 CPU 런이 세션 시간 제한에 걸려 32번째 업데이트쯤에서 끊겼다. 레퍼런스 런도 10개 중 8개가 failed로 끝났다.

원인

학습 전체가 jit scan 하나로 돌아서, 끝나기 전에는 아무것도 저장되지 않았다.

목표

끊긴 런을 이어서 돌려도, 끊기지 않은 런과 결과가 정확히 같아야 한다.

해결

학습을 N업데이트짜리 jit 청크로 나누고, 청크가 끝날 때마다 전체 상태를 저장한다. 같은 명령을 다시 치면 저장된 상태에서 이어진다. 시간 제한이 있는 작업은 max_updates_per_run으로 미리 정한 지점에서 멈춘다.

결과

한 번에 끝낸 런과 5업데이트마다 프로세스를 바꿔 이어 붙인 런을 비교하면 기록된 값 390개 중 다른 값이 0개다. 파라미터가 비트 단위로 같은지는 단위 테스트로도 확인한다.

Problem 5: 태스크를 압도한 호기심 보상

증상

레퍼런스 ICM 런에서 intrinsic reward는 스텝당 7.5 안팎까지 올랐지만 extrinsic reward는 0 근처를 맴돌았다. PLACE_TABLE마저 0%로 떨어졌다.

원인

스케일을 맞추지 않은 forward 모델 오차를 드문드문 나오는 태스크 보상에 그대로 더했다. 에이전트는 새로운 상태만 쫓았다.

목표

평균 크기가 일정하고 태스크 보상보다 작은 탐험 보너스.

해결

보너스를 오차의 running mean으로 나눠 평균을 1로 맞추고 0.01을 곱한다. 처음엔 표준편차로 나눴는데, 제곱 오차는 거의 평균 성분이라 보너스 평균이 12 안팎에 머물렀다.

결과

정규화한 보너스는 스텝당 평균 0.01, 보통 길이의 에피소드로 치면 5 정도다. 수렴하면 20을 넘는 태스크 리턴보다 한참 작다. 다만 이 방식이 실제로 폭주를 막고 탐험을 늘리는지는 아직 대조 실험으로 확인하지 않았다(아래 Experiment Design).

Experiment Design

Problem 5에서 호기심 보너스를 오차의 running mean으로 나눠 스케일을 맞췄다. 그런데 이 정규화가 보너스 폭주를 정말 막는지, 탐험을 정말 늘리는지는 대조 실험으로 확인한 적이 없다. 그래서 두 질문을 따로 세웠다.

  • H1. 폭주 억제: running mean으로 나눈 보너스는 학습 내내 일정한 크기에 머물고, 정규화하지 않거나 표준편차로 나눈 보너스는 보상을 덮어 버리는가?
  • H2. 탐험 개선: running mean 정규화를 쓴 ICM이 호기심 없는 PPO보다 더 많은 업적 종류에 도달하는가? 원래 보상(extrinsic reward)은 깎이지 않는가?

조건

Craftax-Symbolic-v1 PPO 기본 설정과 시드는 모두 같다. ICM 조건끼리는 보너스 계수(0.01)도 같아서, 다른 점은 정규화 방식 하나뿐이다.

조건스텝당 보너스예상
ppo없음기준선
icm_none0.01 · e원본 오차가 크면 보너스가 보상을 덮는다
icm_std0.01 · e / std(e)제곱 오차는 평균 성분이 커서 여전히 너무 크다

icm_ema0.01 · e / EMA(e)오차가 줄어드는 만큼 스케일도 따라간다(업데이트당 감쇠 0.99)

e는 전이마다 계산한 ICM forward 모델 오차다.

측정하는 것

  • 폭주: 전체 보상 크기 중 보너스가 차지하는 비율(icm/bonus_share)과 스텝당 보너스 평균. 학습 마지막 10% 구간에서도 비율이 절반을 넘거나, 보너스가 처음보다 2배 넘게 커지면 폭주로 본다. 초반 구간은 판정에서 뺀다. 그때는 extrinsic reward가 0에 가까워서 제대로 스케일된 보너스도 비율이 높게 나온다.
  • 탐험: 학습 중 한 번이라도 도달한 업적 종류 수, Craftax 점수(업적 성공률의 기하평균), 에피소드당 업적 수.
  • 태스크 성능: extrinsic reward만으로 센 에피소드 리턴. 보너스가 섞이지 않은 값으로 비교한다.

판정 기준

  • 같은 시드끼리 짝지어 ppo와 비교한다. 5천만 스텝보다 짧은 런은 판정하지 않는다.
  • H1 지지: icm_mean은 어느 시드에서도 폭주하지 않고, icm_none이나 icm_std는 폭주한다. 대조군도 폭주하지 않으면 판단을 보류한다.
  • H2 지지: 시드 3개 이상에서, 도달한 업적 종류나 Craftax 점수가 모든 시드에서 ppo보다 높다. 동시에 extrinsic reward 리턴이 모든 시드에서 낮아지지는 않아야 한다.

Miscellaneous Trials & Errors

1. 호기심 보상을 표준편차로 정규화한 시도

처음 ICM을 고칠 때는 보너스를 누적 표준편차로 나눴다. 그래도 보너스는 스텝당 평균 12 안팎이었다. 제곱 예측 오차는 분산보다 평균 쪽이 훨씬 크기 때문이다. running mean으로 나누고 나서야 스케일이 맞았다.

2. CPU 과다 할당

Crafter PPO를 학습시키는 동안 옆에서 테스트를 돌렸더니 학습 속도가 초당 80스텝 정도에서 15스텝으로 떨어졌다. 환경 프로세스 8개와 PyTorch 스레드 풀 2개가 코어 4개를 서로 차지하려 했다. 지금은 torch_threads 옵션으로 환경 워커가 쓸 코어를 비워 둔다.

3. 레퍼런스 그래프 읽기

처음에는 W&B의 "Step" 축을 환경 스텝인 줄 알았다. 알고 보니 PPO 업데이트 횟수였다. 15k 업데이트가 10억 스텝이 되려면 배치가 얼마여야 하는지 거꾸로 계산해서 레퍼런스 런의 배치 크기를 알아냈다.
