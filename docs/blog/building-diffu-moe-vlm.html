1. Overview

Core problem and contribution

The project aimed at an LLM-planned, diffusion / mixture-of-experts agent for Minecraft-like worlds, but its environment returned random pixels and ignored every action, so no result could be measured. This note documents how it became three tested pipelines: a DEPS-style planner on a symbolic tech tree, MoE and diffusion policies on Crafter pixels, and a pure-JAX Craftax trainer that matches the setup of 1B-step reference runs and resumes bit-for-bit after interruption.

2. Key points

A world that can be solved before an agent that solves it: a Gymnasium tech tree with enforced tools, ingredients and fuel takes the default tasks from 0/6 to 6/6, and keeps 6/6 with 30% random action failures through replanning.

Plan quality measured separately from control quality: with prerequisite gathering switched off, a plan that skips steps exhausts its replanning budget; with it on, the same plan succeeds.

MoE PPO and diffusion cloning from pixels: on Crafter, a CNN + top-2-of-4 MoE policy reaches about 3× the random score in 100k CPU steps, and a diffusion policy cloned from it nearly matches its return.

Reading the reference correctly: the reference charts are Craftax-Symbolic at 1e9 steps whose x-axis counts PPO updates, not Crafter at 1e5 steps; the JAX pipeline runs that exact setup.

Determinism as a tested property: a run split into checkpointed chunks across processes reproduces an uninterrupted run with 0 of 390 logged values differing.

3. Methodology

Tech-tree environment. The symbolic world is an MDP over inventories \(s \in \mathbb{N}^{19}\) with macro actions \(a = (\text{verb}, \text{item})\), \(\text{verb} \in \{\text{mine}, \text{craft}, \text{smelt}\}\). An action succeeds only if its tools are held and its ingredients are available; ingredients are consumed, tools are not. A task succeeds when its target item enters the inventory.

DEPS loop. The planner (an LLM or a quantity-aware rule-based fallback) emits a plan; a parser turns it into an ordered list of sub-goal instances (Mine cobblestone x6 becomes six); the selector picks the next pending instance; the controller acts. An instance completes when its item count increases. Three consecutive failures, or 50 steps on one sub-goal, trigger a replan whose prompt includes the inventory and the error message.

PPO. Both learned paths optimise the clipped objective with generalised advantage estimation:

$$L^{\text{CLIP}}(\theta) = \mathbb{E}_t\left[\min\left(r_t(\theta)\hat{A}_t,\ \operatorname{clip}(r_t(\theta), 1-\epsilon, 1+\epsilon)\hat{A}_t\right)\right],\quad r_t = \frac{\pi_\theta(a_t\mid s_t)}{\pi_{\theta_{\text{old}}}(a_t\mid s_t)}$$
$$\hat{A}_t = \sum_{l\ge 0} (\gamma\lambda)^l \delta_{t+l},\qquad \delta_t = r_t + \gamma V(s_{t+1})(1-d_t) - V(s_t)$$

Mixture of experts. A gate produces \(p = \operatorname{softmax}(W_g x + \varepsilon)\); the two largest experts are mixed with renormalised weights, and a load-balancing term keeps experts in use:

$$y = \sum_{i \in \text{top-}k(p)} \frac{p_i}{\sum_{j\in\text{top-}k} p_j} E_i(x),\qquad L_{\text{aux}} = E \sum_{i=1}^{E} f_i\, \bar{p}_i$$

where \(f_i\) is the fraction of inputs routed first to expert \(i\) and \(\bar{p}_i\) its mean gate probability (\(L_{\text{aux}} = 1\) when balanced, \(E\) when collapsed).

Diffusion policy. An action chunk of horizon \(H = 8\) is encoded as one-hot vectors scaled to \([-1, 1]\). The denoiser predicts the clean chunk:

$$\mathcal{L} = \mathbb{E}_{t,\epsilon}\left\| f_\theta\!\left(\sqrt{\bar\alpha_t}\,x_0 + \sqrt{1-\bar\alpha_t}\,\epsilon,\ t,\ \phi(o)\right) - x_0 \right\|^2$$

Sampling uses 10 strided DDIM steps; the first 4 actions are executed before resampling.

Curiosity bonus. The ICM forward error \(e_t\) is normalised by its running mean before scaling, so its average contribution is fixed:

$$r_t = r^{\text{ext}}_t + \beta\,\frac{e_t}{\overline{e}},\qquad \beta = 0.01$$

Crafter score. Achievement success rates \(s_i\) (in %) are combined as \(S = \exp\big(\tfrac{1}{N}\sum_i \ln(1+s_i)\big) - 1\).

Training pipeline. Crafter policies use PyTorch with multiprocess environments. Craftax runs environment, GAE and PPO inside one jax.jit with 1024 envs × 64 steps per update, optimistic resets (64 fresh worlds per step), and full-state checkpoints every few updates.

4. Experimental Results

Environments and metrics

  • Symbolic tech tree: success on six default tasks, steps to success, replans.
  • Crafter: return and Crafter score over 20 episodes on fixed worlds.
  • Craftax-Symbolic-v1: return, achievements per episode, success rate of every achievement; reference ranges from the 1e9-step W&B runs.

Main quantitative results

  • Planner: 0/6 → 6/6 tasks (wooden slab 3 steps, diamond 34); 6/6 with 30% random action failures.
  • Crafter: random 1.56 → MoE PPO 4.63 → diffusion BC 3.56 (score); returns 1.25 / 3.60 / 3.55. The random score matches the published ~1.6%.
  • Diffusion conditioning: clean-sample prediction gives 40/40 exact action-chunk matches; epsilon-prediction produced observation-blind chunks.
  • Craftax (CPU, baseline config): PPO return 1.49 → 6.66 in 6.55M steps; PPO-RNN 5.15 vs. PPO 5.47 at 3.28M steps. COLLECT_WOOD 97%, PLACE_TABLE 90%, MAKE_WOOD_PICKAXE 50% at 6.55M.
  • Reproducibility: 0 of 390 logged values differ between one uninterrupted run and checkpointed chunks across processes; 58 automated tests pass.

5. In-depth Consideration

Technical significance and strengths

  • Every rule of the symbolic world lives in one pure function shared by the environment, the controller and the rule-based planner, so the planner baseline is an exact upper bound and LLM plans can be scored against it.
  • The JAX trainer makes the reference setup a single command on one GPU, and its chunked checkpoints make preemption harmless; 8 of 10 reference runs had ended in a failed state.
  • Each failure in this note (dummy environment, unconditioned diffusion, misread charts, curiosity collapse) was turned into a test or an explicit check.

Limitations and critical review

  • Scale: Craftax results cover 0.3–0.7% of the reference budget with one seed; the end-of-training comparison (PPO ~26, PPO-RNN ~37) has not been run yet.
  • Reference values: ranges were read off chart images and are approximate; the reference runs' own hyper-parameters were not available, so the Craftax baseline defaults were used.
  • Oracle planner: the rule-based planner knows the recipes, so 6/6 is an upper bound, not an LLM result; LLM planning should be measured with prerequisite gathering off.
  • Scope of modules: the trajectory / IMU encoder is validated on synthetic motions only, and the diffusion policy exists only on the PyTorch path.

6. Easy Explanation

Imagine coaching someone to cook a full menu. First you need a kitchen where the stove actually heats and ingredients actually run out; the original project was a kitchen with painted-on appliances, so no recipe could ever work. Then you give them a recipe book (the planner) and teach their hands the techniques (the learned policies). Finally, to compare them with a professional chef, you have to cook the same menu for the same amount of time: the reference results came from a far longer practice session in a different kitchen. Keeping a precise logbook (checkpoints) means a power cut never forces you to start over.

7. In Game Development

Automated solvability checks for crafting systems: the quantity-aware planner computes the exact action sequence to any item, so a change to recipes or drop rates can be checked for unreachable items and for the number of steps a player needs, before any playtest.

Difficulty curves from step counts: steps-to-item (3 for a wooden slab, 34 for a diamond in the toy tree) is a direct, automatable proxy for progression pacing that can be tracked across balance patches.

Hybrid NPCs: a planner chooses goals and learned or scripted skills execute them, which keeps NPC behaviour explainable (the plan is text) while low-level control stays robust; replanning on failure handles blocked paths or missing resources.

Automated playtesting at scale: the JAX pipeline runs tens of thousands of game steps per second on one GPU, and deterministic, resumable runs make agent-based regression tests repeatable across builds.

Capacity within a frame budget: a top-2-of-4 MoE mixes only two experts per input. With sparse dispatch (the current implementation still evaluates all experts for simplicity), this is a route to larger-capacity NPC policies within a real-time frame budget.
