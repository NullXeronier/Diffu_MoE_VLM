0. Before you read

This note assumes neural networks, gradient descent and basic reinforcement-learning vocabulary (state, action, reward). Everything else is summarized below in one line each, linked to the original paper. Each method in the body is explained as why → formula → intuition.

1. Overview

The problem and what I did

The goal was an agent for Minecraft-like worlds where an LLM plans and diffusion / mixture-of-experts policies act. The environment, though, returned random pixels and ignored every action, so nothing could be measured. This note covers how it became three pipelines with tests: a planner in the Describe, Explain, Plan and Select style on a symbolic tech tree, MoE and diffusion policies on Crafter pixels, and a pure-JAX Craftax trainer that uses the published Craftax PPO baseline settings (the reference runs' own config was not available) and, on CPU, resumes bit-for-bit after interruption.

2. Key points

Fix the world first. With a Gymnasium tech tree that checks tools, ingredients and fuel, the default tasks went from 0/6 to 6/6. Replanning keeps them at 6/6 even when 30% of actions fail at random.

Planning and control are measured apart. With prerequisite gathering switched off, a plan that skips steps runs out of replans. Switch it on and the same plan succeeds.

MoE PPO and diffusion cloning from pixels. On Crafter, a CNN with a top-2-of-4 MoE reaches about 3× the random score in 100k CPU steps. A diffusion policy cloned from it gets close to its return.

Read the reference charts properly. They show Craftax-Symbolic at 1e9 steps, not Crafter at 1e5, and their x-axis counts PPO updates. The JAX pipeline runs the same environment and budget with the Craftax baseline hyper-parameters; whether those match the reference runs is unknown.

Determinism is tested. A run split into checkpointed chunks across processes matches an uninterrupted run: 0 of 390 logged values differ.

3. Methodology

3.1 Tech-tree environment

Why: you can only tell whether a plan is correct if the world decides outcomes by fixed rules. A rules-only world without pixels is fast and deterministic, so plan quality can be measured on its own, without control skill getting in the way.

The symbolic world is an MDP over an inventory \(s \in \mathbb{N}^{19}\) and macro actions \(a = (\text{verb}, \text{item})\), \(\text{verb} \in \{\text{mine}, \text{craft}, \text{smelt}\}\). An action succeeds only with the required tool and enough materials; materials are consumed, tools are not. A task succeeds when the goal item enters the inventory.

3.2 Describe, Explain, Plan and Select loop

Why: an LLM rarely writes a perfect plan in one go. The Describe, Explain, Plan and Select approach sends back an explanation of the failure so the LLM can revise the plan, and planning mistakes get fixed while the agent is still running.

The planner (an LLM or a quantity-aware rule-based fallback) emits a plan; the parser turns it into an ordered list of subgoal instances (Mine cobblestone x6 becomes six). The selector picks the next pending instance and the controller acts. An instance completes when the matching item count increases.

3.3 PPO (Proximal Policy Optimization) and GAE (Generalized Advantage Estimation)

Why: with policy gradients, one update that is a bit too large can wreck the policy. PPO reuses each batch for several updates but keeps the policy close to the old one. It is the usual baseline, and the reference Craftax runs use it.

$$L^{\text{CLIP}}(\theta) = \mathbb{E}_t\left[\min\left(\rho_t(\theta)\hat{A}_t,\ \operatorname{clip}\big(\rho_t(\theta), 1-\epsilon_{\text{clip}}, 1+\epsilon_{\text{clip}}\big)\hat{A}_t\right)\right],\quad \rho_t(\theta) = \frac{\pi_\theta(a_t\mid s_t)}{\pi_{\theta_{\text{old}}}(a_t\mid s_t)}$$
$$\delta_t = r_t + \gamma (1-d_t)\, V(s_{t+1}) - V(s_t),\qquad \hat{A}_t = \delta_t + \gamma\lambda\,(1-d_t)\,\hat{A}_{t+1},\qquad \hat{A}_T = 0$$

Intuition: actions with positive advantage \(\hat{A}_t\) become more likely and negative ones less likely. Once \(\rho_t\) moves past \(1\pm\epsilon_{\text{clip}}\) in the direction the advantage pushes, that sample stops contributing gradient. This discourages large policy changes but does not strictly bound them: with several epochs and minibatches the ratio can still end up outside the range. \(\delta_t\) is "what we got minus what we expected". The \((1-d_t)\) factors cut the recursion at episode ends, so an advantage never sums TD errors from the next episode in the same rollout. At the end of a 64-step rollout the last \(V(s_T)\) bootstraps whatever is left. \(\lambda\) trades bias for variance: \(\lambda=0\) uses one TD error, \(\lambda=1\) sums TD errors up to the episode end or the rollout end, whichever comes first. Both training paths treat an episode that ends by time limit as terminal (no bootstrap), as the Craftax baselines do; values just before the limit are slightly biased by this.

3.4 Mixture of Experts

Why: what an agent does in Crafter varies a lot: collecting wood, fighting, crafting. If different experts handle different inputs, you can get more capacity for the same compute, and maybe experts that specialize in different skills. I haven't measured whether they actually specialize.

The gate produces \(p = \operatorname{softmax}(W_g x + \xi)\) and mixes the \(k=2\) most probable experts with renormalized weights. A balance loss keeps experts evenly used.

$$y = \sum_{i \in \text{top-}k(p)} \frac{p_i}{\sum_{j\in\text{top-}k} p_j} E_i(x),\qquad L_{\text{aux}} = E \sum_{i=1}^{E} f_i\, \bar{p}_i$$

Intuition: \(f_i\) is the fraction of inputs routed first to expert \(i\) and \(\bar{p}_i\) its mean gate probability. Perfect balance gives \(L_{\text{aux}} = 1\); collapse onto one expert gives \(E\). Without it, whichever expert is slightly ahead early keeps getting trained and the rest go unused. The noise \(\xi\) makes the gate try other experts early in training.

3.5 Diffusion policy

Why: often more than one action is fine (go around an obstacle on the left or on the right). Regression-style imitation averages them and can end up with the action in between, walking straight into the obstacle. Diffusion learns the whole action distribution and picks one of the options. Generating whole chunks also keeps short stretches of motion consistent.

An action chunk of length \(H = 8\) is represented as one-hot vectors scaled to \([-1, 1]\), and the denoiser \(f_\theta\) predicts the clean chunk \(x_0\) from a noised one.

$$\mathcal{L} = \mathbb{E}_{t,\epsilon}\left\| f_\theta\!\left(\sqrt{\bar\alpha_t}\,x_0 + \sqrt{1-\bar\alpha_t}\,\epsilon,\ t,\ \phi(o)\right) - x_0 \right\|^2$$

Intuition: training noises the expert chunk and asks for the original back. The more noise (smaller \(\bar\alpha_t\)), the less it can be recovered without looking at the observation \(\phi(o)\). The first implementation predicted the noise \(\epsilon\) and, in our experiment, produced observation-independent chunks; switching to predicting \(x_0\) directly gave 40/40 exact chunk matches. My reading is that the noise can mostly be guessed without the observation, while the clean chunk can't.

3.6 Curiosity bonus: ICM (Intrinsic Curiosity Module)

Why: Crafter only gives a reward the first time an achievement is unlocked, so rewards are rare. A bonus for reaching states that are hard to predict keeps the agent exploring in between.

$$r_t = r^{\text{ext}}_t + \beta\,\frac{e_t}{\overline{e}_k},\qquad \overline{e}_k = \text{mean of all errors up to update } k,\qquad \beta = 0.01$$

Intuition: \(e_t\) is ICM's next-state prediction error and \(\overline{e}_k\) the mean of every error seen so far, including the current batch. Dividing by the standard deviation at first left the bonus at about 12 per step in my run, because the error's mean is much larger than its spread; it drowned out the extrinsic reward. Dividing by the running mean fixes the scale, but only on average and only while the error distribution stays put. The first batch averages exactly \(\beta\). After that, the batch average is \(\beta\) times (current mean error / all-time mean error): it drops below \(\beta\) as the forward model improves and rises above it when the agent finds states the model predicts badly. Single steps have no upper bound at all. So the normalization sets how big the bonus usually is. It can't promise the bonus stays small. The experiment at the end of section 4 is meant to find out whether it prevents runaway in practice and whether it helps exploration.

3.7 Crafter score

$$S = \exp\Big(\frac{1}{N}\sum_{i=1}^{N} \ln(1+s_i)\Big) - 1$$

Intuition: \(s_i\) is the success rate (%) of achievement \(i\). An arithmetic mean is high if the agent is good at a few easy achievements. The log in the geometric mean makes even a small gain on a near-0% achievement count for a lot, so agents that cover many achievements score higher.

3.8 Training pipeline and checkpoints

Why: the reference results come from 1B steps of training. At that scale the environment has to run compiled on the GPU too, and a run that takes hours has to pick up exactly where it stopped after an interruption.

Crafter policies use multiprocess environments and PyTorch. Craftax runs environment, GAE and PPO inside one jax.jit, with 1024 environments × 64 steps per update.

  • Optimistic reset: instead of generating a new world for every finished environment, only 64 fresh worlds (1024 ÷ 16) are generated per step and finished environments draw from that pool. World generation is the most expensive part of a Craftax step, so this is much faster.
  • Reading the x-axis: one update is 1024 × 64 = 65,536 environment steps, so 1B steps is about 15,258 updates. The "15k" on the reference x-axis means 1B steps, not 15k steps.
  • Checkpoints: the full training state is saved every few updates and the next process loads it and continues.

4. Experimental Results

Environments and metrics

  • Symbolic tech tree: success on six default tasks, steps to success, replans.
  • Crafter: return and Crafter score over 20 episodes on fixed worlds.
  • Craftax-Symbolic-v1: return, achievements per episode, success rate of every achievement; reference ranges from the 1e9-step W&B runs.

Main quantitative results

  • Planner: 0/6 → 6/6 tasks (wooden slab 3 steps, diamond 34); 6/6 with 30% random action failures.
  • Crafter: random 1.56 → MoE PPO 4.63 → diffusion BC 3.56 (score); returns 1.25 / 3.60 / 3.55. The random score matches the published ~1.6%.
  • Diffusion conditioning: clean-sample prediction gives 40/40 exact action-chunk matches; epsilon-prediction produced observation-blind chunks.
  • Craftax (CPU, baseline config): PPO return 1.49 → 6.66 in 6.55M steps; PPO-RNN 5.15 vs. PPO 5.47 at 3.28M steps. COLLECT_WOOD 97%, PLACE_TABLE 90%, MAKE_WOOD_PICKAXE 50% at 6.55M.
  • Reproducibility: 0 of 390 logged values differ between one uninterrupted run and checkpointed chunks across processes; 68 automated tests pass.

Crafter score (higher is better)

Geometric mean of 22 achievement success rates, 20 evaluation episodes on the same worlds. MoE PPO is about 3× random, with diffusion imitation behind it.

Planner: steps to solve each task

Rule-based planner, all six tasks solved. Longer tech-tree paths take more steps (Figure 1).

Craftax-Symbolic-v1: episode return over the first millions of steps

Default config, one seed, CPU. Reference runs reach about 26 (PPO) and 37 (PPO-RNN) at 1B steps.

Designed, not yet run: curiosity bonus normalization

I divided the bonus by its running mean (3.6) after seeing the reference ICM run collapse. I haven't checked yet whether that fix works. There are two questions:

  • H1. Does the mean-normalized bonus stay at a steady size, while an unnormalized or std-normalized bonus takes over the reward?
  • H2. Does that ICM reach more kinds of achievements than PPO without curiosity, without lowering the extrinsic return?

Five arms share the Craftax PPO baseline config and seeds: no curiosity (ppo), raw error (icm_none), divided by the std (icm_std), by the running mean (icm_mean) and by an exponential moving mean (icm_ema). The ICM arms also share \(\beta = 0.01\), so normalization is the only difference.

$$\text{share} = \frac{\sum |\beta\, e_t / \text{scale}|}{\sum |\beta\, e_t / \text{scale}| + \sum |r^{\text{ext}}_t|}$$

Runaway is judged by the share of the reward that is bonus. A run counts as runaway if the share is still above 0.5 over the last 10% of training, or if the bonus per step grew more than 2×. Early training is left out because the extrinsic reward is nearly zero there and even a well-scaled bonus dominates. Exploration is measured by the number of achievement types ever reached and by the Craftax score; task performance by the extrinsic-only return.

Each arm is compared with ppo on the same seed. H1 holds if icm_mean never runs away while icm_none or icm_std does. H2 holds if, over at least 3 seeds, achievement types or score beat ppo on every seed and the extrinsic return is not lower on every seed. Runs under 5·10⁷ steps get no verdict.

The code (run_icm_ablation.py, analyze_icm_ablation.py), unit tests and a CPU debug run are done. The GPU runs (5 arms × 3 seeds × 1e9 steps, about 50 hours) have not happened, so both questions are still open.

5. In-depth Consideration

What worked

  • All the rules of the symbolic world are in one pure function that the environment, the controller and the rule-based planner all call. That makes the rule-based planner an exact upper bound to score LLM plans against.
  • With the JAX trainer, a 1e9-step run with the baseline settings is one command on one GPU. It checkpoints every chunk (50 updates by default), so a preempted run loses at most the updates since the last checkpoint. 8 of 10 reference runs had ended in a failed state.
  • Every failure in this note (dummy environment, diffusion that ignored its condition, misread charts, curiosity collapse) now has a test or a check in the code.

Limitations

  • Scale: Craftax results cover 0.3–0.7% of the reference budget with one seed; the end-of-training comparison (PPO ~26, PPO-RNN ~37) has not been run yet.
  • Reference values: ranges were read off chart images and are approximate; the reference runs' own hyper-parameters were not available, so the Craftax baseline defaults were used.
  • Oracle planner: the rule-based planner knows the recipes, so 6/6 is an upper bound and says nothing about how an LLM planner does. LLM plans should be measured with prerequisite gathering switched off.
  • Scope of modules: the trajectory / IMU encoder is validated on synthetic motions only, and the diffusion policy exists only on the PyTorch path.
  • ICM effect: mean normalization sets the typical scale of the bonus but does not bound it, and whether it prevents runaway or improves exploration has not been tested with a controlled run (end of section 4).
  • Determinism: bit-identical reruns and resumes were verified on CPU only. GPU runs may differ in the last bits.

6. Easy Explanation

Say you're teaching someone to cook a full menu. First you need a kitchen where the stove gets hot and the ingredients get used up. The original project was a kitchen with the appliances painted on the wall, so no recipe could ever work. Then you give them a recipe book (the planner) and teach their hands the techniques (the learned policies). To compare them with a professional chef, they have to practise the same menu for as long. The reference results came from much longer practice in a different kitchen. And if you keep a careful logbook (checkpoints), a power cut doesn't send you back to the start.

7. In Game Development

Checking that a crafting system can be completed: the quantity-aware planner works out the exact action sequence for any item. After changing recipes or drop rates, you can check for items that became unreachable and for how many steps a player now needs, before anyone playtests.

Difficulty curves from step counts: the number of steps to reach an item (3 for a wooden slab, 34 for a diamond in the toy tree) tracks progression pacing directly. It can be computed automatically and compared from one balance patch to the next.

Hybrid NPCs: a planner picks goals and learned or scripted skills carry them out. Because the plan is text, you can see why an NPC did something, and the low-level control stays as reliable as before. When something fails, such as a blocked path or a missing resource, the NPC replans.

Automated playtesting at scale: the JAX pipeline runs tens of thousands of game steps per second on one GPU. Runs are deterministic and can resume, so an agent-based regression test gives the same result on every build.

Bigger models within a frame budget: a top-2-of-4 MoE mixes only two experts per input. If only those two were actually computed (the current code still runs all four, to keep it simple), a larger NPC policy could fit in a real-time frame budget.
