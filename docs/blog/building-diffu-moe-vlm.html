0. Before you read

This note assumes neural networks, gradient descent and basic reinforcement-learning vocabulary (state, action, reward). Everything else is summarized below in one line each, linked to the original paper. Each method in the body is explained as why → formula → intuition.

1. Overview

Core problem and contribution

The project aimed at an LLM-planned, diffusion / mixture-of-experts agent for Minecraft-like worlds, but its environment returned random pixels and ignored every action, so no result could be measured. This note documents how it became three tested pipelines: a planner in the Describe, Explain, Plan and Select style on a symbolic tech tree, MoE and diffusion policies on Crafter pixels, and a pure-JAX Craftax trainer that matches the setup of 1B-step reference runs and resumes bit-for-bit after interruption.

2. Key points

A world that can be solved before an agent that solves it: a Gymnasium tech tree with enforced tools, ingredients and fuel takes the default tasks from 0/6 to 6/6, and keeps 6/6 with 30% random action failures through replanning.

Plan quality measured separately from control quality: with prerequisite gathering switched off, a plan that skips steps exhausts its replanning budget; with it on, the same plan succeeds.

MoE PPO and diffusion cloning from pixels: on Crafter, a CNN + top-2-of-4 MoE policy reaches about 3× the random score in 100k CPU steps, and a diffusion policy cloned from it nearly matches its return.

Reading the reference correctly: the reference charts are Craftax-Symbolic at 1e9 steps whose x-axis counts PPO updates, not Crafter at 1e5 steps; the JAX pipeline runs that exact setup.

Determinism as a tested property: a run split into checkpointed chunks across processes reproduces an uninterrupted run with 0 of 390 logged values differing.

3. Methodology

3.1 Tech-tree environment

Why: to judge whether a planner wrote a correct plan, the world must decide outcomes by fixed rules. A rules-only world with no pixels is fast and deterministic, so plan quality can be measured independently of control skill.

The symbolic world is an MDP over an inventory \(s \in \mathbb{N}^{19}\) and macro actions \(a = (\text{verb}, \text{item})\), \(\text{verb} \in \{\text{mine}, \text{craft}, \text{smelt}\}\). An action succeeds only with the required tool and enough materials; materials are consumed, tools are not. A task succeeds when the goal item enters the inventory.

3.2 Describe, Explain, Plan and Select loop

Why: an LLM rarely writes a perfect plan in one shot. The Describe, Explain, Plan and Select approach returns an explanation of the failure so the LLM can revise the plan, which lets planning errors be recovered during execution.

The planner (an LLM or a quantity-aware rule-based fallback) emits a plan; the parser turns it into an ordered list of subgoal instances (Mine cobblestone x6 becomes six). The selector picks the next pending instance and the controller acts. An instance completes when the matching item count increases.

3.3 PPO and GAE

Why: with policy gradients, a slightly too large update can collapse the policy. PPO reuses each batch for several updates while keeping the policy close to the old one; it is the most common baseline, and the reference Craftax runs use it.

$$L^{\text{CLIP}}(\theta) = \mathbb{E}_t\left[\min\left(\rho_t(\theta)\hat{A}_t,\ \operatorname{clip}\big(\rho_t(\theta), 1-\epsilon_{\text{clip}}, 1+\epsilon_{\text{clip}}\big)\hat{A}_t\right)\right],\quad \rho_t(\theta) = \frac{\pi_\theta(a_t\mid s_t)}{\pi_{\theta_{\text{old}}}(a_t\mid s_t)}$$
$$\hat{A}_t = \sum_{l\ge 0} (\gamma\lambda)^l \delta_{t+l},\qquad \delta_t = r_t + \gamma V(s_{t+1})(1-d_t) - V(s_t)$$

Intuition: actions with positive advantage \(\hat{A}_t\) become more likely and negative ones less likely, but once the ratio \(\rho_t\) leaves \(1\pm\epsilon_{\text{clip}}\) pushing further no longer increases the objective, so one update cannot move the policy far. \(\delta_t\) is "what we got minus what we expected"; \(\lambda\) chooses between a one-step estimate (\(\lambda=0\): low variance, high bias) and a full-episode one (\(\lambda=1\): the opposite).

3.4 Mixture of Experts

Why: Crafter behaviors differ in kind: collecting wood, fighting, crafting. Letting different experts handle different inputs can add capacity at the same compute or encourage skill specialization. Specialization itself has not been measured in this project yet.

The gate produces \(p = \operatorname{softmax}(W_g x + \xi)\) and mixes the \(k=2\) most probable experts with renormalized weights. A balance loss keeps experts evenly used.

$$y = \sum_{i \in \text{top-}k(p)} \frac{p_i}{\sum_{j\in\text{top-}k} p_j} E_i(x),\qquad L_{\text{aux}} = E \sum_{i=1}^{E} f_i\, \bar{p}_i$$

Intuition: \(f_i\) is the fraction of inputs routed first to expert \(i\) and \(\bar{p}_i\) its mean gate probability. Perfect balance gives \(L_{\text{aux}} = 1\); collapse onto one expert gives \(E\). Without it, whichever expert is slightly ahead early keeps getting trained and the rest go unused. The noise \(\xi\) makes the gate try other experts early in training.

3.5 Diffusion policy

Why: several actions can be good in the same situation (go around an obstacle on the left or on the right). Regression-style imitation averages them and can produce the in-between action, walking into the obstacle. Diffusion learns the whole action distribution and commits to one mode, and generating chunks gives coherent short-horizon motion.

An action chunk of length \(H = 8\) is represented as one-hot vectors scaled to \([-1, 1]\), and the denoiser \(f_\theta\) predicts the clean chunk \(x_0\) from a noised one.

$$\mathcal{L} = \mathbb{E}_{t,\epsilon}\left\| f_\theta\!\left(\sqrt{\bar\alpha_t}\,x_0 + \sqrt{1-\bar\alpha_t}\,\epsilon,\ t,\ \phi(o)\right) - x_0 \right\|^2$$

Intuition: training noises the expert chunk and asks for the original back. The more noise (smaller \(\bar\alpha_t\)), the less it can be recovered without looking at the observation \(\phi(o)\). The first implementation predicted the noise \(\epsilon\) and, in our experiment, produced observation-independent chunks; switching to predicting \(x_0\) directly gave 40/40 exact chunk matches. Our interpretation: guessing the noise is largely solvable without the observation, guessing the clean chunk is not.

3.6 Curiosity bonus (ICM)

Why: Crafter rewards are sparse, given only the first time an achievement is unlocked. A bonus for reaching hard-to-predict states keeps the agent exploring between rewards.

$$r_t = r^{\text{ext}}_t + \beta\,\frac{e_t}{\overline{e}},\qquad \beta = 0.01$$

Intuition: \(e_t\) is ICM's next-state prediction error and \(\overline{e}\) its running mean. Dividing by the standard deviation at first left the error's large mean in place, so the bonus averaged about 12 and drowned out the extrinsic reward. Dividing by the running mean keeps \(e_t/\overline{e}\) near 1 on average, which pins the mean bonus at \(\beta\) and keeps it a helper to the real reward. Whether this actually prevents runaway and helps exploration is the subject of the experiment at the end of section 4.

3.7 Crafter score

$$S = \exp\Big(\frac{1}{N}\sum_{i=1}^{N} \ln(1+s_i)\Big) - 1$$

Intuition: \(s_i\) is the success rate (%) of achievement \(i\). An arithmetic mean rewards being good at a few easy achievements; the log-based geometric mean weighs raising a near-0% achievement heavily, so agents that solve many achievements evenly score higher.

3.8 Training pipeline and checkpoints

Why: the reference results come from 1B-step training. Running at that scale needs the environment compiled onto the GPU as well, and a multi-hour run must continue identically after an interruption.

Crafter policies use multiprocess environments and PyTorch. Craftax runs environment, GAE and PPO inside one jax.jit, with 1024 environments × 64 steps per update.

  • Optimistic reset: instead of generating a new world for every finished environment, only 64 fresh worlds (1024 ÷ 16) are generated per step and finished environments draw from that pool. World generation is the most expensive part of a Craftax step, so this is much faster.
  • Reading the x-axis: one update is 1024 × 64 = 65,536 environment steps, so 1B steps is about 15,258 updates. The "15k" on the reference x-axis means 1B steps, not 15k steps.
  • Checkpoints: the full training state is saved every few updates and the next process loads it and continues.

4. Experimental Results

Environments and metrics

  • Symbolic tech tree: success on six default tasks, steps to success, replans.
  • Crafter: return and Crafter score over 20 episodes on fixed worlds.
  • Craftax-Symbolic-v1: return, achievements per episode, success rate of every achievement; reference ranges from the 1e9-step W&B runs.

Main quantitative results

  • Planner: 0/6 → 6/6 tasks (wooden slab 3 steps, diamond 34); 6/6 with 30% random action failures.
  • Crafter: random 1.56 → MoE PPO 4.63 → diffusion BC 3.56 (score); returns 1.25 / 3.60 / 3.55. The random score matches the published ~1.6%.
  • Diffusion conditioning: clean-sample prediction gives 40/40 exact action-chunk matches; epsilon-prediction produced observation-blind chunks.
  • Craftax (CPU, baseline config): PPO return 1.49 → 6.66 in 6.55M steps; PPO-RNN 5.15 vs. PPO 5.47 at 3.28M steps. COLLECT_WOOD 97%, PLACE_TABLE 90%, MAKE_WOOD_PICKAXE 50% at 6.55M.
  • Reproducibility: 0 of 390 logged values differ between one uninterrupted run and checkpointed chunks across processes; 68 automated tests pass.

Crafter score (higher is better)

Geometric mean of 22 achievement success rates, 20 evaluation episodes on the same worlds. MoE PPO is about 3× random, with diffusion imitation behind it.

Planner: steps to solve each task

Rule-based planner, all six tasks solved. Longer tech-tree paths take more steps (Figure 1).

Craftax-Symbolic-v1: episode return over the first millions of steps

Default config, one seed, CPU. Reference runs reach about 26 (PPO) and 37 (PPO-RNN) at 1B steps.

Designed, not yet run: curiosity bonus normalization

Dividing the bonus by its running mean (3.6) was a fix prompted by the collapsed reference ICM run. Whether the fix works has not been checked. Two questions:

  • H1. Does the mean-normalized bonus stay at a steady size, while an unnormalized or std-normalized bonus takes over the reward?
  • H2. Does that ICM reach more kinds of achievements than PPO without curiosity, without lowering the extrinsic return?

Five arms share the Craftax PPO baseline config and seeds: no curiosity (ppo), raw error (icm_none), divided by the std (icm_std), by the running mean (icm_mean) and by an exponential moving mean (icm_ema). The ICM arms also share \(\beta = 0.01\), so normalization is the only difference.

$$\text{share} = \frac{\sum |\beta\, e_t / \text{scale}|}{\sum |\beta\, e_t / \text{scale}| + \sum |r^{\text{ext}}_t|}$$

Runaway is judged by the share of the reward that is bonus. A run counts as runaway if the share is still above 0.5 over the last 10% of training, or if the bonus per step grew more than 2×. Early training is left out because the extrinsic reward is nearly zero there and even a well-scaled bonus dominates. Exploration is measured by the number of achievement types ever reached and by the Craftax score; task performance by the extrinsic-only return.

Each arm is compared with ppo on the same seed. H1 holds if icm_mean never runs away while icm_none or icm_std does. H2 holds if, over at least 3 seeds, achievement types or score beat ppo on every seed and the extrinsic return is not lower on every seed. Runs under 5·10⁷ steps get no verdict.

The code (run_icm_ablation.py, analyze_icm_ablation.py), unit tests and a CPU debug run are done. The GPU runs (5 arms × 3 seeds × 1e9 steps, about 50 hours) have not happened, so both questions are still open.

5. In-depth Consideration

Technical significance and strengths

  • Every rule of the symbolic world lives in one pure function shared by the environment, the controller and the rule-based planner, so the planner baseline is an exact upper bound and LLM plans can be scored against it.
  • The JAX trainer makes the reference setup a single command on one GPU, and its chunked checkpoints make preemption harmless; 8 of 10 reference runs had ended in a failed state.
  • Each failure in this note (dummy environment, unconditioned diffusion, misread charts, curiosity collapse) was turned into a test or an explicit check.

Limitations and critical review

  • Scale: Craftax results cover 0.3–0.7% of the reference budget with one seed; the end-of-training comparison (PPO ~26, PPO-RNN ~37) has not been run yet.
  • Reference values: ranges were read off chart images and are approximate; the reference runs' own hyper-parameters were not available, so the Craftax baseline defaults were used.
  • Oracle planner: the rule-based planner knows the recipes, so 6/6 is an upper bound, not an LLM result; LLM planning should be measured with prerequisite gathering off.
  • Scope of modules: the trajectory / IMU encoder is validated on synthetic motions only, and the diffusion policy exists only on the PyTorch path.
  • ICM effect: mean normalization bounds the bonus size by construction, but whether it prevents runaway and improves exploration has not been tested with a controlled run (end of section 4).

6. Easy Explanation

Imagine coaching someone to cook a full menu. First you need a kitchen where the stove actually heats and ingredients actually run out; the original project was a kitchen with painted-on appliances, so no recipe could ever work. Then you give them a recipe book (the planner) and teach their hands the techniques (the learned policies). Finally, to compare them with a professional chef, you have to cook the same menu for the same amount of time: the reference results came from a far longer practice session in a different kitchen. Keeping a precise logbook (checkpoints) means a power cut never forces you to start over.

7. In Game Development

Automated solvability checks for crafting systems: the quantity-aware planner computes the exact action sequence to any item, so a change to recipes or drop rates can be checked for unreachable items and for the number of steps a player needs, before any playtest.

Difficulty curves from step counts: steps-to-item (3 for a wooden slab, 34 for a diamond in the toy tree) is a direct, automatable proxy for progression pacing that can be tracked across balance patches.

Hybrid NPCs: a planner chooses goals and learned or scripted skills execute them, which keeps NPC behaviour explainable (the plan is text) while low-level control stays robust; replanning on failure handles blocked paths or missing resources.

Automated playtesting at scale: the JAX pipeline runs tens of thousands of game steps per second on one GPU, and deterministic, resumable runs make agent-based regression tests repeatable across builds.

Capacity within a frame budget: a top-2-of-4 MoE mixes only two experts per input. With sparse dispatch (the current implementation still evaluates all experts for simplicity), this is a route to larger-capacity NPC policies within a real-time frame budget.
