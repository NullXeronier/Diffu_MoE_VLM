From a dummy world to reproducible Craftax

The repository promised a diffusion, mixture-of-experts, vision-language agent for Minecraft-like worlds. An audit showed an agent that could never succeed. This is how it became four tested pipelines, and what the numbers do and do not say.

i
Short version. Fix the world before the agent; measure against the right reference; make every run resumable and deterministic, so a missing result is a compute problem, not a mystery.

Phase 0 · The audit

The environment wrapper returned np.random.randint pixels and its step function was a pass; the inventory never changed, so every task ended at step 999 with success: false. None of the diffusion, MoE, VLM, PPO or IMU components named in the README existed in code.

Other findings
  • The full benchmark crashed after the first task: it called a wandb attribute the logger never had.
  • The README's eval.single_task=true override was silently ignored (the code read a top-level key).
  • Plans were split on a literal backslash-n, so real LLM output was never parsed line by line.
  • The rule-based fallback matched wooden_slab inside the prompt template and returned the slab plan for every task.
  • The data manager looked in the wrong directory and always used hard-coded defaults.
  • Goal embeddings used Python's salted hash(), so they changed on every run.

Phase 1 · Hygiene first

An API-key file, bytecode, W&B runs and Hydra outputs were committed. The key file was removed from history, the repository was re-created from a single clean commit, and a .gitignore now keeps build and run artifacts out. Experiment records were later restored with personal values (email, host name, home paths, GPU UUID) masked, including inside the binary W&B log, which was rewritten record by record so it stays valid.

!
Deleting a file in a new commit does not remove it from history. A leaked key has to be revoked; history rewriting only limits further spread.

Phase 2 · A world that responds

The environment became a symbolic tech tree: mining needs the right pickaxe, crafting consumes ingredients and may need a table, smelting needs a furnace and coal. The DEPS loop on top of it: the planner proposes a plan, a parser turns it into sub-goals, a selector picks the next one, the controller acts, and repeated failures trigger a replan that includes the inventory and the error.

Two details mattered more than expected:

  • Quantities. "Have planks" is not "have three planks". Plans now say Mine cobblestone x6, and a sub-goal completes when its item is obtained, not merely present.
  • Ablations as a measuring stick. With controller.auto_prerequisites=false, a plan that skips steps fails after its replan budget, so the controller no longer hides planning errors.

Result: all six default tasks succeed (wooden slab in 3 steps, diamond in 34), versus 0/6 before.

Phase 3 · Learned policies on Crafter

Crafter gives 64×64 pixels, 17 actions and 22 achievements. The policy is a CNN (or ViT, or a frozen CLIP/SigLIP tower) feeding a top-k mixture-of-experts trunk with a Switch-style load-balancing loss, trained with PPO. A diffusion policy then clones PPO's action chunks and executes them in a receding horizon.

i
A bug worth remembering. The first diffusion model reached a low loss but produced the same action chunk for every observation. With epsilon-prediction, the loss at high noise barely depends on recovering the clean one-hot chunk. Predicting the clean sample directly fixed it: 40 of 40 samples correct on the test task.

Phase 4 · Reproducing the reference runs

The reference W&B charts looked far ahead of the local runs. Reading them closely explained why: they are Craftax-Symbolic runs at 1e9 steps on a GPU (50k–95k steps/s), and their x-axis counts PPO updates. 1e9 / (1024 envs × 64 steps) ≈ 15,258, which is exactly the axis length.

The JAX pipeline runs environment and learner together under jit. Two engineering choices did most of the work:

  • Optimistic resets. World generation dominates a Craftax step; generating only a pool of fresh worlds per step and handing them to finished environments avoids paying it 1024 times.
  • Checkpoint and resume. The full state (parameters, optimizer, environment states, RNG) is saved every few updates. The first long run here was stopped by a session time limit; with resume, the same command continues, and the results match an uninterrupted run bit for bit (0 of 390 logged values differ).

On a 4-core CPU, PPO reached a return of 6.7 after 6.55M steps and PPO-RNN 5.2 after 3.3M, with the same early ordering of achievements as the reference. The end-of-training comparison (PPO ~26, PPO-RNN ~37) needs a GPU, and compare_craftax_run.py checks a finished run against 70 reference ranges.

What happened to the curiosity (ICM) run

Its intrinsic reward climbed to ~7.5 per step while the extrinsic reward stayed near zero, and it lost even basic achievements such as placing a table. The bonus is now divided by its running mean and scaled by 0.01. Dividing by the standard deviation is not enough, because a squared prediction error is mostly mean.

What I would tell myself at the start

  1. Check that the environment can be solved at all before tuning the agent.
  2. Find out exactly which environment, budget and axis the reference used before comparing numbers.
  3. Make determinism and resume a test, not a hope. It turns "the run died" into "re-run the command".
  4. Keep a dumb baseline (random, rule-based) in every table; it catches metric bugs.
